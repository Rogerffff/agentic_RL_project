好的，让我用通俗的方式解释这份计划中涉及的异步 RL 核心参数和概念。

同步 vs 异步 RL 的根本区别
同步 RL（你之前跑的 96 步）：


┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐
│ Rollout  │────▶│  Reward  │────▶│ Advantage│────▶│ PPO更新  │
│ 所有样本  │     │ 所有样本  │     │          │     │          │
│ 必须全完成│     │          │     │          │     │          │
└──────────┘     └──────────┘     └──────────┘     └──────────┘
     ▲                                                   │
     └───────────────────────────────────────────────────┘
                    一步完成后，才开始下一步
问题：一个 batch 里最慢的样本决定整步时间。deep search 任务长尾重，有的样本 30 秒就完了，有的要 6 分钟 timeout。所有快的样本都在等最慢的那个。

异步 RL（现在要做的）：


Rollouter（持续产出样本）          Trainer（持续消费样本）
┌─────────────────────┐          ┌─────────────────────┐
│ 样本1 ──完成──▶ Queue │          │ 从Queue取够4个样本   │
│ 样本2 ──完成──▶ Queue │   ────▶  │ 计算reward/advantage │
│ 样本3 ──生成中...     │          │ PPO更新              │
│ 样本4 ──完成──▶ Queue │          │ 每2步同步参数给Rollout│
│ 样本5 ──生成中...     │          └─────────────────────┘
│ ...（持续不停）       │
└─────────────────────┘
核心收益：Rollout 和 Training 解耦。快完成的样本立刻被消费，不用等慢的。GPU 利用率提高，wall time 下降。

逐个参数解释
ASYNC_PROFILE=async_partial
这是 async 的运行模式。有三种：

模式	含义
sync_stream	"假异步"：staleness=0，不允许过期样本，基本等同同步但走 async 代码路径
async_partial	真异步 + 部分恢复：允许过期样本 + 当参数更新时，正在进行的 rollout 可以被 cancel 并用新参数 resume
base	基础 probe，不启用 multi-turn 工具调用，只验证 async 基座
async_partial 是最完整的异步模式。

ppo_mini_batch_size（简写 b）
含义：Trainer 每次 PPO 更新需要收集多少个prompt 样本。

b4：每次更新用 4 个 prompt
b8：每次更新用 8 个 prompt
每个 prompt 又会产出 n 个 rollout，所以实际训练数据量 = b × n。

rollout.n（简写 n）
含义：每个 prompt 并行生成多少个不同的回答。

C-GRPO 的核心机制是组内对比——同一个问题的 n 个回答中，做得好的被奖励，做得差的被惩罚。n 越大，对比越稳定。

n=4（旧训练）：4 个回答比较，信号不太稳
n=8（论文设定）：8 个回答比较，信号更稳定
所以 b4/n8 意味着：4 个问题 × 8 个回答 = 32 条训练轨迹/步。

ASYNC_STALENESS=0.5
含义：允许多大比例的"过期样本"进入训练。

什么是"过期"？异步模式下，Trainer 更新了参数（比如从 version 3 → version 4），但 Rollouter 可能还在用 version 3 的参数生成样本。这些样本的策略概率和当前模型不一致，叫做 stale（过期）。

staleness=0.0：不允许任何过期样本（等于同步）
staleness=0.5：允许 queue 里最多有 50% 的过期样本缓冲
staleness=1.0：允许 100% 缓冲，rollouter 永不暂停
具体机制：它影响 rollouter 的暂停门槛：


max_required_samples = mini_batch_size × (1 + staleness) × trigger_sync_step
当 queue 里积压超过这个数，rollouter 暂停生产。staleness 越大，暂停越晚，吞吐越高，但过期样本越多。

ASYNC_TRIGGER_SYNC_STEP=2
含义：Trainer 每做 2 次 PPO 更新，才把新参数同步给 Rollouter 一次。

为什么不每步都同步？因为参数同步有成本——要暂停 Rollouter、传输权重、清 KV cache、恢复。太频繁会拖慢吞吐。2 是已验证的平衡点。

每次同步后，current_param_version +1。这是 async 里最核心的"版本号"概念。

ASYNC_REQUIRE_BATCHES=1
含义：每次 PPO 更新前需要收集多少个 mini-batch。

1 表示收齐 1 个 ppo_mini_batch_size 的样本就开始更新。如果设 2，就要等 2 个 batch。

ASYNC_MAX_CONCURRENT_SAMPLES=12
含义：Rollouter 最多同时生成多少个 prompt 的 rollout。

每个 prompt 产出 n 个并发生成请求，所以实际并发请求数 = concurrent × n：

12 concurrent × n=8 = 96 个并发生成（这是 review 中指出的显存风险）
之前 probe 验证的是 12 × n=4 = 48 个并发
ASYNC_MAX_QUEUE_SIZE=12
含义：Rollouter → Trainer 之间的消息队列最多积压多少个完成的样本。

防止 Rollouter 产出太快、Trainer 消费不及时导致内存爆炸。

partial_rollout=true
含义：当参数版本更新时，正在进行中的 rollout 可以被取消并恢复。

这是 async_partial 最关键的特性。想象一个 deep search 样本正在第 15 轮工具调用，这时参数从 v2 → v3。不启用 partial 的话，这个样本用 v2 参数生成的结果要么丢弃，要么作为 stale 样本使用。启用 partial 后：

这个样本被 cancel
它的中间状态（搜索历史、工具调用记录、budget 消耗）被保存到 cancel_queue
新参数加载后，它被 resume，从断点继续生成
这样就避免了长 rollout 的浪费。

max_param_span=2
含义：一个 rollout 最多允许跨越 2 个参数版本。

如果一个 deep search 样本非常慢，从 param version 1 开始生成，到 version 3 还没完成，就会被强制终止。防止极端长尾。

rollout.total_rollout_steps
含义：Rollouter 从数据集中取出的总 prompt 数。这不等于 trainer steps。


trainer_steps ≈ rollout_steps / ppo_mini_batch_size
param_syncs ≈ trainer_steps / trigger_sync_step
例如 Stage A：48 / 4 = 12 trainer steps，12 / 2 = 6 次参数同步。

trainer.save_freq
含义：每隔多少个 param_version 保存一次 checkpoint。

注意：是按参数版本号算的，不是按 trainer step 算的。save_freq=1 表示每次参数同步后都保存。

gpu_memory_utilization=0.3
含义：SGLang 推理引擎允许使用的 GPU 显存比例。

0.3 意味着每张 96GB 的卡只给 SGLang ~29GB 用于 KV cache。剩余显存留给模型权重和其他开销。

use_dynamic_bsz=false
含义：关闭 FSDP 的动态 micro-batch 打包。

这是之前 async probe 排查出的 bug fix：动态打包在多 GPU 上可能导致不同 rank 的 micro-batch 数量不一致，让 FSDP 集合通信 hang 住。

enforce_eager=true
含义：强制 SGLang 使用 eager 执行模式（不用 CUDA graph）。

在 async 场景下避免递归问题。

checkpoint_engine.enable=false
含义：关闭 GPU 加速的参数广播引擎。

当前 async 用的是直接的权重同步（update_weights_no_flush + clear_kv_cache），不需要额外的 checkpoint engine。

概念关系图

                    ┌─────────────────────┐
                    │   rollout.n = 8     │
                    │ (每个prompt生成8个答案)│
                    └──────────┬──────────┘
                               │
   ┌───────────────────────────▼───────────────────────────┐
   │                    Rollouter                           │

# Async RL Short Run 与正式训练计划（可执行版）

## Summary

目标是用已经跑通的 async partial 基座，解决旧同步 `b8/n4` 下的两个核心问题：

- 大量样本被 `timeout / budget / truncation` 截断，训练信号不足
- 每步 rollout 规模太小，GRPO/C-GRPO 组内信号不稳定

执行顺序固定为：

1. `Stage 0 eval`：固定 `subset64` sampled eval，选 async 起点  
2. `Stage A`：`b4/n8 @ 64k` 真 gate  
3. `Stage B`：`b8/n8 @ 64k` async short run  
4. `Formal Day-1`：在 `A/B` 之间选最高稳定档位，做 1 天正式 async RL  
5. `Stage C optional stretch`：只在 Formal Day-1 跑稳后，再试 `b16/n8 @ 64k`

硬原则不变：

- `64k` 必须保留
- 第一优先保 `n=8`
- `step90` 不默认盲押，先用 sampled eval 选起点
- `b16/n8` 不在正式训练前关键路径
- 若 `n8` 三档都失败，才允许回退到稳定 `n4`

## Stage 设计

### Stage 0：起点评估 Gate

评估对象固定为：

- 必做：`SFT`、`step90`
- 选做：`step70`，仅当 checkpoint 已在盘上且无需额外折腾

起点选择规则固定为：

- 先按 `outcome_reward mean` 排序
- 若前两名差距小于 `0.03`，优先 `task_unfinished` 更低者
- 若仍接近，再优先 `termination_rollout_timeout` 更低者
- 若某候选满足：
  - `task_unfinished > 0.70` 或
  - `termination_rollout_timeout > 0.45`
  则不作为 async 起点

结论规则固定为：

- `step90` 只有过线才作为默认 async 起点
- 否则回退到 `step70`
- 若 `step70` 不在场或也不过线，则回退到 `SFT`

后续所有训练模式都显式接收：
- `ASYNC_START_MODEL_PATH=<选中的 HF checkpoint>`

### Stage A：`b4/n8 @ 64k` 真 Gate

固定几何：

- `actor_rollout_ref.actor.ppo_mini_batch_size=4`
- `actor_rollout_ref.rollout.n=8`
- `ASYNC_STALENESS=0.5`
- `ASYNC_MAX_CONCURRENT_SAMPLES=12`
- `ASYNC_MAX_QUEUE_SIZE=12`
- `rollout.total_rollout_steps=48`
- `trainer.save_freq=1`

budget 策略：

- 第一轮完全沿用 formal 默认 budgets
- 仅当主要坏因是 `termination_rollout_timeout`，且细粒度 tool budget 并不高，才允许补一个 A' 对照：
  - `wall: 360 -> 480`
  - `real_wall: 720 -> 960`
  - 其余 budget 不动
- 仅当主要坏因是 `response_limit`，才允许补一个 `max_tool_response_length=5000` 对照
- 不允许先放大 `tool/search/open/find` budget

### Stage B：`b8/n8 @ 64k` Async Short Run

只有 Stage A 通过才进入。

固定几何：

- `actor_rollout_ref.actor.ppo_mini_batch_size=8`
- `actor_rollout_ref.rollout.n=8`
- `ASYNC_STALENESS=0.5`
- `ASYNC_MAX_CONCURRENT_SAMPLES=16`
- `ASYNC_MAX_QUEUE_SIZE=16`
- `rollout.total_rollout_steps=128`
- `trainer.save_freq=2`

如果 Stage B 下：

- `trainer/idle_ratio` 仍明显偏高
- 且 `total_partial_num` 增长偏慢

才允许唯一上调项：

- `ASYNC_STALENESS: 0.5 -> 1.0`

### Formal Day-1

正式默认档位选择规则：

- Stage B 通过：正式默认 = `b8/n8`
- 否则 Stage A 通过：正式默认 = `b4/n8`
- 只有 A/B 都失败，才允许回退到 `fallback_b8_n4_64k`

`formal_best_1day` 必须**完整继承**被选中 stage 的几何：

- 若选 `b4/n8`：
  - 继承 Stage A 的 `staleness=0.5`
  - 继承 `max_concurrent=12`
  - 继承 `max_queue=12`
- 若选 `b8/n8`：
  - 继承 Stage B 的 `staleness=0.5` 或已验证的 `1.0`
  - 继承 `max_concurrent=16`
  - 继承 `max_queue=16`

1 天预算下的默认步数：

- `seconds_per_rollout_step = total_wall_time / rollout.total_rollout_steps`
- `formal_rollout_steps = floor(0.8 * 86400 / seconds_per_rollout_step)`
- 向下取最近的 `32` 倍数

checkpoint 保存频率按 `current_param_version` 设计：

- `formal_param_versions = floor(formal_rollout_steps / (ppo_mini_batch_size * require_batches * trigger_sync_step))`
- `trainer.save_freq = max(2, floor(formal_param_versions / 4))`

### `fallback_b8_n4_64k`

这个兜底模式必须固定为“镜像 Stage B，只把 `n=8` 改成 `n=4`”：

- `actor_rollout_ref.actor.ppo_mini_batch_size=8`
- `actor_rollout_ref.rollout.n=4`
- `ASYNC_STALENESS=0.5`
- `ASYNC_MAX_CONCURRENT_SAMPLES=16`
- `ASYNC_MAX_QUEUE_SIZE=16`
- `rollout.total_rollout_steps=128`
- `trainer.save_freq=2`

### `stretch_b16_n8_64k`

只在 Formal Day-1 跑稳后再做，不进入正式训练前关键路径。

固定为：

- `actor_rollout_ref.actor.ppo_mini_batch_size=16`
- `actor_rollout_ref.rollout.n=8`

- `ASYNC_MAX_CONCURRENT_SAMPLES=16`
- `ASYNC_MAX_QUEUE_SIZE=16`

- `trainer.save_freq=1`

## 验收标准

### Stage A

必须同时满足：

- 正常完成 `48 rollout steps`
- 至少 `2` 次成功 param sync
- `fully_async/partial/total_partial_num > 0`
- completed sample 中出现 `param_version_start != param_version_end`
- 用**最近 3 个有效 trainer steps 的 trailing mean** 判定：
  - `outcome_reward mean > 0`
  - `task_unfinished mean < 0.70`
  - `termination_rollout_timeout mean < 0.45`
- 不出现 blocker 级错误

### Stage B

必须满足 Stage A 全部标准，并额外满足：

- `64 trajectories/update` 下稳定完成 `128 rollout steps`
- 用最近 `3` 个有效 trainer steps 的 trailing mean 判定：
  - `trainer/idle_ratio mean < 0.35`
  - `outcome_reward mean` 不显著差于 Stage A
  - `termination_rollout_timeout mean` 不显著差于 Stage A

固定记录诊断指标：

- `stale_trajectory_processed`
- `stale_trajectory_ratio`

定义统一为：

- `stale_trajectory_ratio_3step = Δ stale_trajectory_processed / (3 * ppo_mini_batch_size * require_batches * rollout.n)`

其中 `Δ stale_trajectory_processed` 取最近 `3` 个有效 trainer steps 的增量。
这个指标当前只做诊断，不做硬 gate。

### Formal Day-1

必须同时满足：

- 无 blocker 级错误
- `n=8` 持续成立，除非已明确进入 fallback 模式
- reward 与梯度信号持续非零
- 末段与中段都不出现明显的 `unfinished/timeout` 崩塌
- 至少产生可评估 checkpoint

run 后固定评测对比对象明确为：

- `SFT`
- **实际选中的 async 起点 checkpoint**
- `Formal Day-1 final checkpoint`
- 如需要，再加一个中间 checkpoint

不再把对比对象隐含写成固定 `step90`。

## Assumptions

- 当前 async infra 修复已视为稳定：真实 param sync、CaRR async agent、DONE drain、SGLang no-flush update、pause 前 clear_kv_cache、dynamic_bsz 关闭。
- 第一轮正式 async 训练默认从 **model-only** checkpoint restart，不做 strict resume。
- `64k`、`120 turns`、`tool=6000` 是“与旧同步 RL 和论文主设定可比”的最低口径。
- `n8` 是优先目标，但不是死规定；若 `A/B` 都失败，允许回退到稳定 `n4` 档作为工程兜底。
